# Путь масштабирования — Счёт&Контроль

## Этап 0 — сейчас
- 1 VPS (TimeWeb Cloud), Docker Compose: Postgres + Redis + API + фронтенд
- Мультиарендность работает: самостоятельная регистрация организации/владельца,
  изоляция данных по `org_id` из JWT
- Ручной деплой через `deploy.sh` (git pull + docker compose up -d --build)
- Ежедневный `pg_dump` в локальную папку на том же сервере

## Этап 1 — домен и HTTPS
- Купить/подключить домен, направить A-запись на IP сервера
- Поставить reverse-proxy (Caddy или nginx + certbot) перед API и фронтендом — автоматический Let's Encrypt сертификат
- Перевести `NEXT_PUBLIC_API_URL` / `CORS_ORIGIN` на `https://домен`
- Закрыть прямой доступ к портам 3000/3001 снаружи, пускать только через 443
- Единственный сознательно отложенный блокер по итогам аудитов 2026 —
  прод по-прежнему работает по HTTP/IP; решение владельца, следующий
  логичный шаг, как только появится домен

## Открытый бэклог — запланировано, не в текущей работе

Единый список нерешённых пунктов, перенесённых из ранее отдельных
аудит-документов (AUDIT*.md, RESEARCH_DOCUMENT_RECOGNITION_2026.md — все
удалены как источники, покрытые этим файлом; см. git-историю для полного
текста находок).

- **Trust Score как предиктивная модель риска** — ✅ частично закрыто:
  `GET /counterparties/:id/overdue-risk` (`services/api-gateway/src/lib/overdueRisk.js`)
  теперь даёт объяснимый прогноз риска просрочки контрагента (доля
  просроченных из последних счетов, средняя задержка, тренд), отдельно от
  статичного поля `counterparties.trust_score`, которое не тронуто (на нём
  завязаны прогноз кассовых разрывов и ABC-анализ). Показан раскрывающейся
  строкой на /counterparties. Дальнейшее развитие — учёт внешних данных,
  ML-модель вместо эвристики — по-прежнему отдельная будущая задача, ждёт
  накопленной статистики по большему числу организаций.
- **Партнёрская интеграция с ЭДО (СБИС/Диадок)** — запланирована на будущее,
  намеренно вне текущего скоупа. Продукт сознательно работает со «Счетами»
  как коммерческими документами, а не «Счетами-фактурами»/УПД по смыслу
  НК РФ — полноценная ЭДО-интеграция потребует отдельного юридического и
  API-анализа. Архитектурная точка расширения уже заведена и закоммичена
  (`services/api-gateway/src/lib/edoProvider.js` — неподключённая заготовка
  клиента по образцу `yookassa.js`, `isConfigured()` всегда `false` без env,
  плюс nullable-колонки `edo_document_id`/`edo_status` на `outgoing_invoices`),
  но не активирована — реальный SDK/API провайдера, роут и UI появятся
  только вместе с началом этой работы, не раньше.
- **Повторяющиеся/шаблонные счета** — низкий приоритет, узкий кейс
  (регулярные абонентские счета), осознанно не взято в предыдущий релиз.
- **PDF-квитанция об оплате** — простой PDF-акт из данных `payments` по
  аналогии с уже существующими PDF/Excel для исходящих счетов; не сделано.
- **Полноценный экран управления пользователями организации** — приглашение
  есть, отдельного UI со списком/сменой роли/деактивацией нет (см. Этап 2).
- **Открытые архитектурные вопросы, требуют отдельного решения, не оценены:**
  - двусторонняя модель долга («кому я должен» / «мне должны») — влияет на

  - мультиорганизационный доступ для бухгалтеров-аутсорсеров (один бухгалтер

## Рыночный контекст 2026 (Discovery Team) и новые пункты бэклога

Синтез рыночного исследования по нише AP/AR-автоматизации (мировой рынок
AP-automation, $3.8–6.9 млрд, CAGR 10–21%) и конкурентного анализа. Полный
текст находок — у Discovery Team, здесь только выводы, влияющие на бэклог.

- **Touchless processing** (обработка счёта без участия человека) —
  ключевой тренд рынка, даже у лидеров закрыт лишь на ~33%. У продукта есть
  реальный шанс на паритет: OCR-распознавание одиночных и пакетных счетов
  уже реализовано и работает (см. git-историю задач OCR-REAL,
  OCR-TEXT-UNIFY) — остаётся довести его до флагманского позиционирования,
  а не рассматривать как вспомогательную функцию.
- **AI-based data capture** становится отраслевым гигиеническим минимумом,
  а не преимуществом — не повод для отдельной задачи, важно не отстать.
- **Real-time payments** (в РФ — Система быстрых платежей для юрлиц) — в
  продукте не реализовано. **Новый пункт бэклога**, будущее направление,
  не текущая задача.
- **Мобильность** — тренд, частично закрыт (см. MOBILE-RESPONSIVE,
  MOBILE-NAV-FIX в git-истории).
- **Fraud prevention** как отдельная фича рынка ложится на уже
  существующий Trust Score / индикатор риска просрочки
  (`overdueRisk.js`, см. выше). **Новый пункт бэклога: explainable Trust
  Score** — развитие текущего предиктивного индикатора в публичную,
  объясняемую пользователю метрику (не просто число, а видимые причины
  оценки). Будущая задача, не в текущем скоупе.
- **Конкуренты**: СБИС/Saby и МойСклад (РФ) — жалобы пользователей на
  непрозрачное растущее ценообразование и резкую смену интерфейса без
  предупреждения; это ниша для акцента на предсказуемость. Публичная
  фиксация принципа «тариф не меняется без предупреждения за N дней» —
  реальное публичное бизнес-обязательство перед клиентами, требует
  решения Founder о конкретном N; сознательно НЕ опубликовано в этом
  раунде (решение — пропустить до отдельного рассмотрения), остаётся
  открытым пунктом бэклога. Trust Score как визуальная метрика доверия к
  контрагенту — редкое УТП, почти не встречается у конкурентов РФ.
  Bill.com (мировой конкурент) — жалобы на медленную обработку платежей,
  слабые фильтры/поиск и глубину детализации по позициям — зеркалит
  риски, уже фигурировавшие в собственных аудитах продукта.
- **Telegram-уведомления** — решение не добавлять уже принято ранее и
  остаётся в силе (см. «Add release plan for consolidated 2026 audit
  backlog (SMS/Telegram excluded per decision)» в git-истории);
  противоречий с этим пунктом нет.
- **Вне скоупа технической разработки — маркетинг/GTM, адресовано
  напрямую Founder/Growth, не разработке:** клиентские видео-кейсы и
  отзывы, позиционирование через конкретную боль клиента вместо общей
  категории продукта. Зафиксировано как заметка, задачей бэклога не
  является.
