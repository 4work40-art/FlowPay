# Путь масштабирования — Счёт&Контроль

## Этап 0 — сейчас
- 1 VPS (TimeWeb Cloud), Docker Compose: Postgres + Redis + API + фронтенд
- Мультиарендность работает: самостоятельная регистрация организации/владельца,
  изоляция данных по `org_id` из JWT
- Ручной деплой через `deploy.sh` (git pull + docker compose up -d --build)
- Ежедневный `pg_dump` в локальную папку на том же сервере

## Этап 1 — домен и HTTPS
- Купить/подключить домен, направить A-запись на IP сервера
- Поставить reverse-proxy (Caddy или nginx + certbot) перед API и фронтендом — автоматический Let's Encrypt сертификат
- Перевести `NEXT_PUBLIC_API_URL` / `CORS_ORIGIN` на `https://домен`
- Закрыть прямой доступ к портам 3000/3001 снаружи, пускать только через 443
- Единственный сознательно отложенный блокер по итогам аудитов 2026 —
  прод по-прежнему работает по HTTP/IP; решение владельца, следующий
  логичный шаг, как только появится домен

## Этап 3 — самостоятельная регистрация организаций (multi-tenant) — выполнено
- ✅ Форма регистрации новой организации + владельца (`POST /api/v1/auth/register`, страница `/register`)
- ✅ Free-тариф — 5 счетов (`invoice_limit` default), лимит блокирует создание счетов сверх лимита
- ✅ Backend модуляризован: `routes/` (auth, dashboard, invoices, payments, counterparties,
  outgoingInvoices, organizations, users, audit, admin, billing, documents, bankImport, analytics, public)
  + `lib/` (db, auth, http, audit, plans, inn, dadata, mailer и др.)
- ✅ Биллинг через ЮKassa, `organizations` — единый источник истины по тарифу/лимиту
  (таблица `subscriptions` — вторичная, синхронизируется вместе с `organizations` в одной транзакции)
- ✅ Публичная кабинет-панель `/admin` для владельца платформы, доступ только
  по флагу `is_platform_admin`, который **не назначается автоматически** ни
  при каком деплое/миграции (см. раздел «Безопасность» в README.md)

## Открытый бэклог — запланировано, не в текущей работе

Единый список нерешённых пунктов, перенесённых из ранее отдельных
аудит-документов (AUDIT*.md, RESEARCH_DOCUMENT_RECOGNITION_2026.md — все
удалены как источники, покрытые этим файлом; см. git-историю для полного
текста находок).

- **Trust Score как предиктивная модель риска** — сейчас `trust_score`
  контрагента/организации считается на лету как описательная метрика (доля
  счетов, оплаченных без просрочки/списания/спора среди закрытых), не
  предиктивная модель. Переход к предиктивной оценке риска (с учётом истории
  просрочек, динамики, возможно — внешних данных) — отдельная будущая
  задача, требует накопленной статистики по большему числу организаций,
  прежде чем есть смысл её строить.
- **Партнёрская интеграция с ЭДО (СБИС/Диадок)** — запланирована на будущее,
  намеренно вне текущего скоупа. Продукт сознательно работает со «Счетами»
  как коммерческими документами, а не «Счетами-фактурами»/УПД по смыслу
  НК РФ — полноценная ЭДО-интеграция потребует отдельного юридического и
  API-анализа. Точка расширения под будущего провайдера ЭДО в коде пока не
  заведена (`services/api-gateway/src/lib/edoProvider.js` не существует) —
  появится вместе с началом этой работы, не раньше.
- **Повторяющиеся/шаблонные счета** — низкий приоритет, узкий кейс
  (регулярные абонентские счета), осознанно не взято в предыдущий релиз.
- **PDF-квитанция об оплате** — простой PDF-акт из данных `payments` по
  аналогии с уже существующими PDF/Excel для исходящих счетов; не сделано.
- **Полноценный экран управления пользователями организации** — приглашение
  есть, отдельного UI со списком/сменой роли/деактивацией нет (см. Этап 2).
- **Открытые архитектурные вопросы, требуют отдельного решения, не оценены:**
  - двусторонняя модель долга («кому я должен» / «мне должны») — влияет на
    модель данных, требует решения, прежде чем оценивать реализацию;
  - мультиорганизационный доступ для бухгалтеров-аутсорсеров (один бухгалтер
    — несколько организаций) — тоже структурный вопрос.
